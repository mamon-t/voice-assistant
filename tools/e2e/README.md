# tools/e2e — сквозные проверки привязки вывода к окну

Регрессионный стенд для `[output] pin_window` / `pin_mode`: проверяет, что
продиктованный текст действительно попадает в целевое окно, а не «успешно
уходит в никуда» (xdotool возвращает 0, даже когда приложение отбросило
события — грабля №24).

## Что внутри

| Файл | Назначение |
|---|---|
| `probe.cpp` | тестовое Qt-окно: `QLineEdit` + перехват сырых xcb-событий. Пишет в дамп-файл текст и счётчики нажатий — настоящих (`real`, XTest) и синтетических (`synthetic`, XSendEvent). Не требует libxcb-dev: из события читается только первый байт. |
| `run-e2e.sh` | 13 сценариев на Xvfb + openbox. |
| `CMakeLists.txt` | цель `probe` (линкуется только с Qt5::Widgets). |

## Запуск

```bash
# зависимости стенда (не проекта):
sudo apt install xvfb openbox xdotool xclip x11-utils
sudo apt install x11-xkb-utils   # setxkbmap: раскладка us,ru для детерминированной посимвольной печати

cd build && cmake .. -DSHERPA_ONNX_OLD_CXX_ABI=ON && make -j4   # соберёт и probe
bash tools/e2e/run-e2e.sh
```

Норма — `ИТОГ: сценариев 13, проверок ok=… fail=0 / ВСЁ ЗЕЛЁНОЕ`.

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `VOICE_ASSISTANT_BIN` | `<repo>/build/src/voice-assistant` | каким бинарником тестировать |
| `E2E_DISPLAY` | `:99` | дисплей; если X там нет, стенд сам поднимет Xvfb |
| `E2E_KEEP_X` | `0` | `1` — не гасить поднятый стендом Xvfb/openbox при выходе |

Стенд можно гонять и внутри живой графической сессии — он не перехватывает
клавиатуру и работает на отдельном дисплее, — но во время прогона лучше не
дёргать мышь: сценарии переключают фокус программно и проверяют его обратно.

## Сценарии

1. **activate + буфер обмена** — текст в привязанное окно, фокус возвращается;
2. **sendevent + буфер обмена** — синтетика в расфокусированное Qt-окно доходит
   (`synthetic>0`), фокус не тронут;
3. **окно уже в фокусе** — самый частый случай диктовки: доставка идёт БЕЗ
   `--window`, всегда настоящими событиями (XTest) — пробник подтверждает
   `synthetic==0`, фокус не мигает, ложного предупреждения о потерянной
   привязке нет. (Прежняя доставка `--window` в сфокусированное окно на живом
   Cinnamon + XED/GTK3 молча не доходила — грабля №29);
4. **activate + посимвольная печать** — кириллица в расфокусированное окно
   (доставка только через активацию), события настоящие, в логе разовое
   предупреждение о гонке `MappingNotify`. Единственный сценарий с повторами
   (до 3 попыток): посимвольная печать после переезда фокуса подвержена
   среде-гонке (см. «Известные особенности»), три неудачи подряд — всё равно
   однозначный FAIL;
5. **pin_restore_focus=false** — фокус остаётся в целевом окне;
6. **закрытое окно** — привязка снимается с предупреждением
   («привязанное окно … недоступно»), текст уходит в активное окно;
7. **своё окно** (`WM_CLASS=voice-assistant`) — `--pin-info` печатает ОТКАЗ
   и возвращает 1; `--type --pin-active` не привязывается
   (сценарий «запись начали кликом по меню лотка»);
8. **--pin-info** — диагностика: активное окно, настройки `[output]`,
   решение о привязке;
9. **sendevent + две вставки подряд** — в расфокусированное окно;
10. **две вставки подряд (activate)** — проверка живости окна на каждой вставке;
11. **--window WID** — явная привязка без `--pin-active`;
12. **без привязки** — текст идёт в текущее активное окно;
13. **ошибки CLI** — коды возврата 2.

## Известные особенности окружения

* Если в ТЕКУЩЕЙ группе раскладки X-сервера нет кириллицы, `xdotool type`
  для каждого символа временно переназначает keycode, и приложение может
  декодировать нажатия ещё **старой** раскладкой (гонка `MappingNotify`):
  символы случайно теряются или подменяются — и в синтетике (`sendevent`), и
  (реже, при смене фокуса вплотную к печати) в настоящих событиях
  (`activate`). Замерено на стенде: `ru` первой группой — 8/8 чисто, `us`
  первой — ~25% сбоев. Стенд поэтому делает своему Xvfb
  `setxkbmap -layout ru,us`. В живой сессии с `method=xdotool` раскладка в
  момент вставки может быть любой (пользователь её переключает!) — ещё один
  довод в пользу `method=auto`: способ «буфер обмена + Ctrl+V» от раскладки
  и гонок не зависит вовсе. Подробности — troubleshooting.md §18.
* openbox на свежепостроенных окнах иногда рапортует об активации, не
  переместив фокус (`_NET_WM_DESKTOP` ещё не выставлен). Инжектор это
  перепроверяет и повторяет активацию; стенд между созданием окна и первой
  вставкой выдерживает паузу.
* `xdotool` в релизной версии 3.20160805.1 не имеет `getwindowclassname` —
  код читает WM_CLASS запасным путём через `xprop` (`x11-utils`). На стенде
  это проверяется сценарием 6.
* В Wayland-сессии стенд не работает в принципе: xdotool требует X.
