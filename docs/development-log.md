# Рабочие заметки

Хронология решений и ошибок. Держим отдельно от README: здесь то, как проект
устроен **изнутри** и на какие грабли мы наступили, а не как им пользоваться.

---

## Итерация 1. Выбор архитектуры

Задача: диктовка и правка текста голосом в Linux, в любом поле ввода, офлайн,
на слабом железе (Celeron, 16 ГБ), с обучением на подсказках пользователя
и с голосовыми командами режимов.

Решения:

* **ASR/VAD — sherpa-onnx, а не Vosk.** Vosk проще, но у sherpa-onnx есть
  и Silero VAD, и несколько семейств offline-моделей, и C++ API, и готовые
  ONNX-модели под русский. Один источник зависимостей вместо двух.
* **Ввод текста — не `xdotool` в лоб.** Для X11 он годится, но для Wayland
  и голой TTY нужен `ydotool` (`/dev/uinput`). Поэтому ввод спрятан за
  интерфейс `ITextInjector` — смена бэкенда не трогает контроллер.
* **Команды — детерминированный словарь, а не классификатор интентов.**
  На Celeron нейросетевой классификатор лишний, а словарь покрывает задачу
  и расширяется файлом.
* **Каркас — Qt5** (`QAudioInput`, трей, `QSettings`, D-Bus через
  `QDBusAbstractAdaptor`), C++17.

## Итерация 2. Скелет

Интерфейсы `IAudioCapture`, `IVad`, `IRecognizer`, `ITextInjector`,

## Итерация 3. Интеграция sherpa-onnx: десять ошибок API

Первая реализация VAD и ASR писалась по памяти и не собралась. Реальный API
сверили с установленными заголовками (`cxx-api.h` 66.0 KB, `c-api.h` 165.2 KB)
и исходниками sherpa-onnx.

| Было | Стало |
|---|---|
| `VoiceActivityDetectorConfig` | `VadModelConfig` |
| `config.model_config.silero_vad.*` | `config.silero_vad.*` |
| `make_unique<VoiceActivityDetector>(config)` | `VoiceActivityDetector::Create(config, seconds)` |
| `vad->Detected()` | `vad->IsDetected()` |
| `make_unique<OfflineRecognizer>(config)` | `OfflineRecognizer::Create(config)` |
| `rec->DecodeStream(&s)` | `rec->Decode(&s)` |
| `s.GetResult()` | `rec.GetResult(&s)` |
| `try/catch` вокруг `Create` | проверка `Get() == nullptr` (исключений C API не бросает) |
| свой `Ort::Env`/`Ort::Session` для Silero | VAD из sherpa-onnx, ONNX Runtime отдельно не нужен |
| `signals: void speechStarted() override;` | сигналы наследуются из `IVad`, `override` недопустим |

Отдельно: один `OfflineStream` на каждый чанк аудио и склейка текста давали
рваный результат — нестриминговую модель надо кормить целой фразой.

## Итерация 4. Модели: SenseVoice не знает русского

Изначально ставили SenseVoice-small, исходя из того, что «русский работает
хорошо». Проверка это опровергла. Замер на одной и той же русской фразе,
официальным бинарником `sherpa-onnx-offline` (то есть обёртка ни при чём):

```
SenseVoice     : RIVIE PALII IT RDS A GLSS OF OONICAL BONE POEODA   (lang=<|yue|>)
SenseVoice, zh : 开放时间早上九点至下午五点                            (идеально)
Whisper tiny   : На бортех стар работает в любом поле вода
Whisper base   : На борте к стаработают в любом поле в вода
zipformer-ru   : набор текста работает в любом поле ввода            ✓
GigaAM v3      : набор текста работает в любом поле ввода            ✓
```

SenseVoice удалена. Основным движком стал `small-zipformer-ru` (110 МБ,
RTF 0.06), запасным — GigaAM v3 (MIT, точнее на шуме, в 3–5 раз медленнее).
Подробные таблицы — в [models.md](models.md).

Там же выяснилось:

* GigaAM доступен в sherpa-onnx в готовом ONNX (4 модели), Python в рантайме
  не нужен;
* пунктуацию умеют только `v3_e2e_*`, которых в ONNX нет;
* hotwords работают лишь у transducer-моделей и лишь в `modified_beam_search`;
* `modified_beam_search` точнее `greedy_search` (greedy терял начало фразы).

## Итерация 5. Профили, пайплайн, интеграция

* `AsrProfile` + `RecognizerFactory` — модель выбирается конфигом, приложение
  знает только `IRecognizer`.
* `VoicePipeline` — вся речевая цепочка в одном классе, контроллер остаётся тонким.
* `TextPostProcessor` — голосовые знаки, заглавные, точка в конце.
* `TransducerRecognizer` (бывший `ZipformerRecognizer`) — переименован, когда
  оказалось, что тем же конфигом грузится и GigaAM RNN-T.
* `NemoCtcRecognizer` — для GigaAM CTC.
* Реализованы заглушки: `CommandParser`, `CommandDictionary` (26 команд),
  `XdotoolInjector`, `HotwordsManager::reload()`, `DBusInterface::reloadHotwords()`.
* `src/CMakeLists.txt` собирает `voice-assistant-core` — цель, которую `tests/`
  ждал с самого начала.

Ключевой эксперимент итерации: ASR **проглатывает** диктантные слова, если их
не бустить. Добавление «точка», «запятая», «вопросительный знак» в hotwords
вернуло их в распознавание, после чего голосовая пунктуация заработала.
`VoicePipeline` примешивает эти слова к подсказкам пользователя автоматически.

## Итерация 6. Первый запуск на живом железе и проверка правописания

Проект впервые запустился на машине разработчика: микрофон → AGC → VAD → ASR →
постобработка → вставка через буфер обмена. Распознано с первого раза:

```
ASR[zipformer]: 0.97 с -> "проверка"
ASR[zipformer]: 2.60 с -> "расшифруй-ка мне длинное сообщение"
```

Первый запуск обнажил две проблемы, обе не в коде распознавания:

1. **В конфиге был неверный путь к каталогу моделей** — ASR не создался, и
   приложение выглядело рабочим: `startRecording()` отрапортовал «Recording
   started», чанки честно шли через AGC в никуда. Ошибка ушла сигналом
   `errorOccurred` из конструктора контроллера, то есть в момент, когда
   подписчиков ещё не было (`TrayIcon` создаётся позже).
   Сделано: режим `--check` с построчной проверкой всех путей, `Mode::Error`
   при сбое тракта, отказ стартовать без пайплайна, `lastError()` и догоняющее
   уведомление в трее.
2. **Вставка через буфер затирает его содержимое** — на каждой фразе.
   Сделано: `preserve_clipboard` (по умолчанию true) возвращает прежний текст
   через `clipboard_restore_ms`.

Затем закрыт последний пункт исходного ТЗ — режим проверки правописания.
`AspellChecker.cpp` был 0 байт при пяти объявленных функциях в заголовке:
сборка проходила, пока класс никто не использовал, и гарантированно падала
при первом же подключении `Mode::Spellcheck`. Вместо него — `HunspellChecker`
на hunspell: русский словарь `hunspell-ru` (3.4 МБ) поддерживается, в отличие
от aspell-ru, не обновлявшегося с 2000-х. Замер на словаре Debian bookworm:
«прверка» → варианты «проверка, поверка, привертка», «помошника» → «помощника»
в списке; корректные слова не помечаются.

Там же поймана новая грабля: C++ API hunspell (`hunspell.hxx`) принимает
`std::string` и поэтому зависит от `_GLIBCXX_USE_CXX11_ABI`. При сборке
проекта со старым ABI (под предсобранные sherpa-onnx) и системном libhunspell
с новым линковка падает. Перешли на чистый C API (`hunspell.h`, `char*`) —
он от ABI не зависит. Ровно та же причина, по которой sherpa-onnx держит
`c-api.h` отдельно от `cxx-api.h`.

## Итерация 7. Первая настоящая диктовка: два дефекта

Разработчик прочитал вслух газетный текст, приложение отработало от микрофона до
вставки. Результат обнажил две проблемы, которые на коротких тестовых фразах
не воспроизводились.

**1. Между фразами не было пробела.** VAD режет речь на сегменты, каждый
вставляется отдельным `typeText()`. На длинном тексте это дало
«…двадцать лет назад.Сегодня вот маленький.Профессиональный боксёр…».
Добавлен `TextPostProcessor::needsLeadingSpace(previous, next)` — чистая
статическая функция, поэтому она покрыта тестами: пробел добавляется, если
предыдущая вставка не кончилась пробелом/переводом строки, а следующая не
начинается со знака препинания или закрывающей кавычки. Отключается
`[output] space_between_segments=false`.

**2. Скор бустинга диктантных знаков был взят с потолка.** Первая версия
ставила 1.0 «чтобы помягче». Замер на живой записи показал, что это ровно
та граница, на которой модель снова теряет «точку»:

| Скор | «точка» |
|---|---|
| 1.00 / 1.25 / 1.50 | потеряна |
| 1.75 / 2.00 | на месте |

Контроль на фантомные вставки: речь без диктантных слов при 2.0 распозналась
чисто. Итог — дефолт 2.0, порог 1.75 задокументирован.

Заодно найден дефект дедупликации: «точка» присутствует и в словаре команд
(как `Command::punctuation`), и в списке диктантных знаков. Контроллер передаёт
её с суффиксом `":2.00"`, а `VoicePipeline` сравнивал строки целиком и добавлял
вторую запись `"точка :2.00"`. Дедупликация переведена на базовую фразу.

**Что осталось непонятным.** Качество распознавания газетного текста
невысокое: «Сорок ионер», «и с буквой но форме точки», «Кованный на сайте
как бы». Гипотезы — быстрая непрерывная речь без пауз (VAD склеивает длинные
сегменты), слабая small-модель, настройки AGC, либо фантомная вставка
«точки» из-за бустинга. Без записи этого прогона проверить нельзя: нужен
WAV того же чтения, прогнанный через все четыре профиля и с разными скорами.

## Итерация 8. Хоткей, запись микрофона, диагностика

Три вещи, без которых проект нельзя «тестить в хвост и гриву».

**Глобальный хоткей** (`IHotkeyListener` + `EvdevHotkeyListener`). Читает
`/dev/input/event*` напрямую — работает в X11, Wayland и TTY, системные
хоткеи DE не нужны. Разбор событий вынесен в `handleEvent(input_event)` и
покрыт тестами на синтетических событиях, поэтому проверяется без железа:
нажатие, отпускание, автоповтор, чужие клавиши, модификаторы (левый и правый
Ctrl — одно и то же). `EVIOCGRAB` по умолчанию выключен: перехват устройства
эксклюзивный, основная клавиатура ушла бы из-под X целиком.

**Запись микрофона в WAV** (`WavWriter`, `--record`, пункт в трее, методы D-Bus).
Закрывает главную диагностическую дыру: раньше нельзя было получить снимок
живого тракта, и спор «модель или микрофон» был неразрешим. Теперь два снимка —
сырой микрофон (`--record`, без AGC) и то, что слышит ASR (`mic_check_source=agc`) —
сравниваются напрямую. Корректность заголовка подтверждена внешним читателем
(питоновский `wave` видит 16000 Гц / моно / 16 бит / ровно записанную длину
и амплитуду).

**`--check` расширен**: валидирует спецификацию клавиши через `configure()`
(без обращения к `/dev/input`), считает читаемые устройства в `/dev/input`
и подсказывает `usermod -aG input`, показывает каталог записей и источник.

Попутно: `[text] auto_punctuate` разделён на `capitalize` и `add_final_dot` —
раньше одним ключом выключались оба, а точка в конце нужна не всегда
(диктовка отдельных слов, поиск, пароли).

Дефолт `[hotkey] grab` изначально был `true`, и это была ошибка: без
скопированного `settings.ini` приложение перехватило бы клавиатуру. Исправлено
на `false` до того, как кто-нибудь успел наступить.

## Итерация 9. Диктовка не должна мешать печатать

Замечание пользователя: «полная блокировка клавиатуры — это не дело. Ладно,
когда диктовка и есть работа, а если по ходу надо заметки писать к файлу,
с которым я работаю?»

Проверка показала, что блокировки в коде нет: `EVIOCGRAB` выключен
(`[hotkey] grab=false`), `XGrabKeyboard`/`XGrabKey` в проекте не используются
вообще — evdev только слушает события. Но вредный совет «`grab=true` решает
проблему» в troubleshooting.md был, а дефолт `Options::grab` в заголовке
оставался `true`. Оба исправлены.

Настоящих конфликтов оказалось четыре, и все они — про вывод текста, а не
про клавиатуру:

1. результат уходит в окно, которое в фокусе **в момент прихода** (через
   0.5–2 с после фразы), а не в то, куда диктовали;
2. способ «буфер обмена + Ctrl+V» затирает буфер на `clipboard_restore_ms`;
3. микрофон слышит стук клавиш, и VAD делает из него сегмент;
4. напечатанное и продиктованное перемешиваются в одной строке.

**Цель вывода (`OutputTarget`).** `Mode` описывает, что делать с речью,
`OutputTarget` — куда класть результат; понятия ортогональны. Вторая цель —
`FileInjector`: один markdown-файл на день,
`~/.local/share/voice-assistant/notes/YYYY-MM-DD.md`, каждая запись строкой
с меткой времени. Файл не зависит ни от фокуса, ни от клавиатуры, ни от буфера
обмена, поэтому конфликт №1–№2 исчезает целиком, а №4 перестаёт иметь значение:
заметки лежат отдельно от рабочего текста. Переключение — голосом («заметка» /
«в редактор»), из трея, по D-Bus, из консоли (`--note`) или конфигом
(`start_target=notes`).

`Command::Type::SetTarget` обрабатывается в `executeCommand()` **до** проверки
`editing_in_dictation`. Иначе сказанное «заметка» пропало бы именно в режиме
диктовки, где оно нужнее всего: это маршрутизация, а не правка текста.

**`pin_window`.** Окно запоминается в начале записи (`xdotool getactivewindow`),
вставка идёт через `--window WID`. Честно написано, что `xdotool --window`
работает через `XSendEvent` и часть приложений такие события игнорирует, —
поэтому опция выключена по умолчанию и проверяется пользователем на своём
редакторе. В песочнице X-сервера нет, проверить это нечем.

**`TypingGuard`.** evdev и так видит все нажатия, поэтому добавлен сигнал
`keyActivity()`: любая клавиша, кроме самого хоткея и модификаторов из его
комбинации (иначе `ctrl+space` глушил бы сам себя). Пока с последнего нажатия
прошло меньше `[audio] typing_guard_ms`, чанк не уходит в VAD/ASR. Запись в WAV
при этом не прерывается: снимок тракта обязан показывать всё, иначе его нельзя
сравнивать с тем, что слышит ASR. По умолчанию выключено — при одновременной
речи и печати слова резались бы. По окончании записи в лог пишется, сколько
аудио выброшено.

**Политика `EVIOCGRAB`.** Собрана в одну статическую `shouldGrab()`, которая не
трогает дескрипторы и потому тестируется без железа. При `grab=true` и пустом
`grab_devices` устройства, похожие на полноценную клавиатуру (≥20 букв и
≥5 цифр в маске `EVIOCGBIT(EV_KEY)`), не перехватываются — то есть основная
клавиатура не уйдёт из-под X, даже если опцию включить по ошибке. Для педали
есть `grab_devices` (подстрока имени или путь).

**Проверка.** 45 проверок в `VoiceUnitsTest` (+13). Цепочка WAV → VAD → ASR →
пунктуация → файл заметок прогнана вживую новым флагом `tools/vad-asr-test
--notes` на русской записи 7.68 с: RTF 0.07, две записи легли в один файл дня,
заголовок написан один раз, кириллица и метки времени на месте. Второй прогон
(11.84 с, «запятая»/«вопросительный знак») подтвердил, что голосовая
пунктуация в заметках работает так же, как в окне.

Три падения на первом прогоне тестов — все три настоящие баги, см. грабли
№20–№22.

## Итерация 10. `pin_window` молча не печатал

Жалоба пользователя: «режим pin_window не напечатал вообще ничего в редакторе,
хотя лог виден. F8 собирает с микрофона данные, расшифровывает, но куда выводит
— непонятно».

**Разбор показал, что чинить надо не один баг, а три, и главный из них —
отсутствие адреса в логе.** Итерация 9 написала в комментарии «честно про
ограничение: XSendEvent принимают не все» и на этом остановилась: опцию
выключили по умолчанию, а проверять было не на чем — в песочнице X-сервера не
было. На этот раз X-сервер подняли (Xvfb + openbox) и проверили всё руками.

**Что подтвердилось экспериментально** (Xvfb 1.21.1, openbox, xdotool
3.20160805.1, два тестовых клиента: голый Xlib и Qt5-окно с `QLineEdit`,
перехватывающее сырые `xcb`-события и печатающее флаг `send_event`):

1. `xdotool … --window WID` действительно выбирает способ доставки по фокусу.
   В исходнике (`xdo.c`, `_xdo_send_key`) это буквально:
   `if (window == CURRENTWINDOW) use_xtest = 1; else { xdo_get_focused_window(…);
   if (focuswin == window) use_xtest = 1; }` — иначе `XSendEvent`.
2. Qt синтетику **принимает**: `xdotool type --window WID "привет"` в
   расфокусированное Qt-окно дошёл, в логе `SYNTH … send_event=1`, и `QLineEdit`
   заполнился. Значит, «все приложения игнорируют XSendEvent» — неправда;
   игнорируют браузеры, LibreOffice, Java и часть терминалов.
3. Кириллица через `--window` работает независимо от раскладки: xdotool сам
   временно переназначает keycode (`state=0x2000` в событии — признак
   подменённой группы).
4. **Код возврата `xdotool` при отброшенной синтетике всё равно `0`.** Отсюда
   и «в логе всё успешно»: `runProcess()` не видел ошибки, а предупреждение
   печаталось один раз — в момент установки привязки, за секунды до вставки.
5. `windowactivate --sync` на живом окне занимает 6–64 мс, `windowfocus` — 4 мс.
   На закрытом окне обе команды возвращают 1 с `BadWindow` — значит, смерть
   окна определяется надёжно.
6. `xdotool type "-текст"` без `--file -` падает с кодом 1: аргумент,
   начинающийся с дефиса, getopt принимает за опцию. `--file -` от этого
   защищает, и он в коде уже был.

**Причина №1, которую эксперимент не показал, а показал код: привязка к окну
самого помощника.** Запись можно начать кликом по меню трея, а в X11
всплывающее меню — отдельное окно, и `getactivewindow` вернёт именно его.
Весь продиктованный текст уезжает в меню, которое закрывается вместе с текстом.
В логе при этом «успех». Теперь `captureTargetWindow()` сравнивает WM_CLASS
с `[output] own_window_class` и PID с `applicationPid()` и отказывается
привязываться к своим окнам, loudly.

**Решение: способ доставки вынесен в чистую функцию.** Новый заголовок
`output/WindowTarget.h` без единой зависимости от X11 — `decideWindowTarget()`
принимает WID привязки, WID активного окна, признак «окно живо», режим и список
своих окон, а возвращает способ доставки и куда вернуть фокус. Именно её
невозможность проверить тестами и была корнем проблемы: логика жила внутри
`typeViaClipboard()`/`typeViaXdotool()` вперемешку с вызовами `QProcess`.

| Было | Стало |
|---|---|
| один способ: всегда `--window WID` | `pin_mode=activate` (по умолчанию) или `sendevent` |
| `activate`: `windowactivate --sync` → пауза `pin_activate_ms` → печать **без** `--window` настоящими событиями → возврат фокуса | фокус возвращается только если `pin_restore_focus=true` и окно-источник известно |
| при неудачной активации — молча `--window` | план Б `windowfocus`, при неудаче — `lastError()` и `reportError()` с адресом |
| привязка к мёртвому окну | `windowExists()` при каждой вставке: привязка снимается, текст идёт в активное окно |
| привязка к окну помощника | отказ + предупреждение с WM_CLASS и PID |
| в лог — один раз при установке привязки | каждая вставка: `текст (17 симв.) -> 4194310 «document.txt — Kate» [активация + настоящие события]` |

Один `DeliveryScope` на всю вставку (RAII): при откате «буфер не сработал →
`xdotool type`» окно активировалось бы дважды и фокус мигал бы на каждом
сегменте. Решение `resolveTarget()` принимается один раз и передаётся в оба
способа.

**Диагностика, которой не хватало.** Две новые опции CLI работают без
микрофона, моделей и GUI — то есть проверяют ровно ту часть тракта, которая
ломается:

```bash
./src/voice-assistant --pin-info                                  # что запомнится и каким способом
./src/voice-assistant --type "проверка раз" --pin-active --delay 3000
```

**Проверка.** 59 проверок в `VoiceUnitsTest` (+14: таблица решений
`WindowTarget` — 8 случаев, парсинг `pin_mode`, дефолты и чтение `.ini`,
отрицательная пауза, dry-run с привязкой). Сквозной прогон на Xvfb + openbox:
6 сценариев, 11 проверок, все зелёные — `activate` и `sendevent` с буфером
обмена, `activate` с посимвольным вводом кириллицы, `pin_restore_focus=false`,
привязка к закрытому окну (текст не пропал, предупреждение в логе), привязка
к окну с чужим `own_window_class` (отклонена). Один прогон сначала «упал»
на ожидании: при `pin_restore_focus=false` фокус должен остаться в редакторе,
а тест ждал «не тронут» — ошибка была в тесте, не в коде.

Грабли №24–№26 ниже — из этой итерации.

## Итерация 11. XED: «стою в редакторе — и всё равно не вставляет»

Первый полевой прогон привязки на живом десктопе: Linux Mint (Cinnamon),
X11, редактор XED (GTK3). Команда `--type "проверка раз" --pin-active
--delay 3000` без переключения окон — самый частый сценарий настоящей
диктовки — дала ровно тот симптом, который задача H, казалось бы, починила:

```
XdotoolInjector: текст (12 симв.) -> 83886197 «Несохранённый документ 2» [синтетика (--window)]
ВСТАВЛЕНО: «проверка раз» (12 симв.)
```

— и пустой редактор.

**Причина.** В `decideWindowTarget()` была ветка «окно уже в фокусе →
доставляем через `--window`: xdotool сам переключится на XTest, раз окно
сфокусировано». На стенде (Xvfb + openbox + Qt-пробник с перехватом сырых
событий) это подтверждалось замером: `real=5, synthetic=0`. На живом
Cinnamon + XED — нет: доставка ушла через `--window`, и GTK3 её молча
проигнорировал (проверка «сфокусированности» внутри xdotool опирается на
`XGetInputFocus`, который под Mutter-подобными WM не обязан совпадать с
`_NET_ACTIVE_WINDOW`; плюс GTK/ibus не обязаны принимать `send_event`).
Грабля №29.

**Урок.** Поведение, замеренное на стенде под одним WM, нельзя переносить
на все WM и тулкиты. Когда есть путь, от WM не зависящий, — выбираем его:
для сфокусированного окна печать БЕЗ `--window` — это всегда XTest, всегда
настоящие события, ровно как ручной ввод. Ветка переписана на
`Delivery::ActiveWindow`, в `WindowTarget` добавлен флаг `pinLost`, чтобы
«окно уже в фокусе» не путалось с настоящей потерей привязки в
предупреждениях лога.

**Попутно** e2e-стенд (`tools/e2e/`, 13 сценариев / 47+ проверок) поймал ещё
две настоящие ошибки итерации 10: запасной путь WM_CLASS через `xprop` брал
`res_name` вместо `res_class` (защита от своего окна молча не работала —
грабля №28), а возврат фокуса вплотную к последнему нажатию терял последний
символ посимвольной печати (Qt отбрасывает клавиши, пришедшие уже неактивному
окну) — добавлена пауза 60 мс перед возвратом. Плюс два усиления: проверка,
что фокус ДЕЙСТВИТЕЛЬНО переехал после `windowactivate` (WM может
рапортовать успех, не переместив фокус), и PID-страховка защиты от своих
окон, когда WM_CLASS не прочитался.

**Проверка.** `VoiceUnitsTest` 59/59 (три теста `WindowTarget` переписаны
под новое решение), e2e 13/13 на Xvfb, чистая сборка. Ждём подтверждения
на живом XED.

Грабли №24 и №25 опасны тем, что обе выглядят как успех: `xdotool` возвращает
ноль, приложение логирует вставку, а текст не появляется. Единственное лечение
— писать в лог **адрес и способ** доставки, а не только факт вызова. Грабля №26
поймана тестом `configPinWindowReadsIni`, написанным раньше кода: без него
защита от №25 была бы мертворождённой.

Грабли №20 и №21 — из одной серии: код выглядит правильно, компилируется без
предупреждений и молча делает не то. Обе пойманы тестами, написанными до
проверки на живом железе, — то есть ровно тем, ради чего тесты и пишутся.
В обоих случаях проверка «на глаз» была невозможна: кириллица в
`QLatin1String` и непоследовательные коды клавиш не видны ни в диффе, ни в логе.

Отдельная история: первый тест словаря команд «проходил» по счётчику
(`added == 3`), но фразы не находились — из-за грабли №6 файл команд
записывался кракозябрами. Счётчик при этом не врал: структурно строки
разбирались правильно. Вывод — в тестах проверять не только количество,
но и содержимое.
