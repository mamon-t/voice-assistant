# Contributing to voice-assistant

Спасибо за интерес к проекту. Ниже — краткие правила для воспроизводимой разработки и изменений.

## Окружение и сборка

Требования и зависимости описаны в [README.md](README.md) (системные пакеты, sherpa-onnx, модели, конфиг).

Типовой цикл разработки:

```bash
mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
# при использовании предсобранного sherpa-onnx с old ABI:
# cmake .. -DSHERPA_ONNX_OLD_CXX_ABI=ON -DCMAKE_BUILD_TYPE=Release
make -j"$(nproc)"
ctest --output-on-failure
```

Диагностика окружения без запуска GUI/микрофона:

```bash
./src/voice-assistant --check
```

## Стиль кода

- C++17, Qt5. Проектные соглашения и архитектура — см. [docs/architecture.md](docs/architecture.md).
- Для форматирования используется `.clang-format` (запуск вручную, например `clang-format -i` для изменённых файлов). Не переформатируйте весь репозиторий без отдельного согласования.
- Предпочитайте небольшие, атомарные изменения с понятным описанием.

## Тесты

- Unit-тесты: `ctest` из каталога сборки (`QT_QPA_PLATFORM=offscreen ctest --output-on-failure` в CI).
- E2E-сценарии привязки вывода к окну: `tools/e2e/run-e2e.sh` (требуется Xvfb/openbox; не входит в `ctest`).

Перед отправкой изменений убедитесь, что релевантные тесты проходят локально.

## Pull Request

- Один PR — одна логическая задача.
- В описании укажите: что изменено, как проверить, есть ли влияние на конфигурацию/совместимость.
- Если меняется поведение или публичный интерфейс (CLI, D-Bus, `settings.ini`) — обновите документацию (`README.md`, `docs/*.md`) в том же PR.

## Сообщения об ошибках

При создании issue по возможности приложите:
- версию/коммит, дистрибутив Linux, способ установки (`.deb/.rpm`/сборка из исходников);
- вывод `voice-assistant --check` (без чувствительных данных);
- шаги воспроизведения, ожидаемое и фактическое поведение, релевантные логи.
